# 背景音按回复标签切换，由 Agent 单独发一条音轨

状态：accepted · 2026-10-27

通话中按对话进展循环播放背景音（呻吟声床），分 5 档强度。档位由 LLM 在每段回复开头用一个行内标签给出，Segmenter 解析并去掉标签，Agent 在这段回复开始播放时交叉淡化到对应档位，背景音作为一条独立的 WebRTC 音轨发给浏览器。网页右上角增加背景音开关，默认开启。

功能来自同级项目 `realtime-sex-voice-call`，本 ADR 记录不照搬其实现的原因。

## 档位

| 档位 | 含义（按整段场景迄今为止的气氛判断，不按单句关键词） | 素材 |
|---|---|---|
| `idle` | 调情、暧昧，尚未进入身体接触 | 无（静音） |
| `low` | 轻吻、抚摸、缓慢升温 | `low`，10s |
| `mid` | 正在进行，有喘息呻吟 | `mid`，10s |
| `high` | 激烈、加快节奏 | `high`，28s |
| `climax` | 高潮、顶点 | `climax`，15s |

素材来自 `~/Desktop/voice/` 的 4 个文件（4 个文件内容各不相同）。旧项目 `public/sfx/` 下的 4 个 mp3 是同一个文件的副本，ogg 只有 1 秒左右，都不使用。

## 决策

1. **行内标签，不用 JSON**。LLM 在每段回复的开头写一个 `<bg:mid>`，用尖括号和情绪标签 `[喜]` 区分开。Segmenter 识别出这个标签后把它从文字里去掉，挂在这段回复上，并且不在标签处切段。TTS 和字幕都看不到标签，流式合成与首段降延迟（ADR 0006）不受影响。
2. **一段回复一个档位**，和情绪的处理方式一致（`emotionScope: 'reply'`）。只看回复里的第一个标签，后面的标签丢弃。缺少标签或标签无法识别时，保持当前档位。
3. **只认标签，不做关键词兜底**。档位可以升也可以降，由模型决定，不设“只许升档”的规则。
4. **在回复开始播放时切换**。以 Agent 状态变为 speaking、且播放的不是语气词作为回复开始出声的时刻（“回复的第一帧 TTS 音频”只表示音频已生成，排在语气词后面时还没播出，不能用）：只要回复开始出声，就交叉淡化到新档位，比如淡出约 1.5 秒、新档位淡入约 1.5 秒，进入 `idle` 时淡出到静音。回复在出声前被打断就不切换。
5. **背景音由 Agent 播放**。用 `@livekit/agents` 自带的 `BackgroundAudioPlayer` 发布一条独立音轨（`background_audio`）。它的音源接受音频帧的异步迭代器，交叉淡化和循环在我们自己写的帧生成器里完成。浏览器把它当作远端 WebRTC 音频播放，所以在回声消除的参考信号里，不会被麦克风收进去再触发 VAD 和打断。前端不需要再写播放逻辑。
6. **档位清单用数据描述，提示词由清单生成**。在 `<AMBIENCE_DIR>/manifest.json` 里写明每个档位的 id、给模型看的中文说明、素材文件、音量和淡入淡出时长。规则段落从清单生成，再拼到角色指令后面。它和 `_rules.md` 分开，`LLM_SHARED_RULES=false` 时也会加上。
7. **按角色开启，素材不进 Git**。在角色 front matter 里加 `ambience: true`，没写的角色不加规则、不发音轨。素材和清单只放在部署目录，由 `AMBIENCE_DIR` 指定（HK 上是 `/var/lib/ptoy/resources/ambience`），需要单独上传到服务器，仓库只提交清单的格式说明和转换脚本。`AMBIENCE_DIR` 没设置或目录缺失时，Agent 照常通话，只是不播放背景音，并在启动日志里说明原因。
8. **素材预先转成 48kHz 单声道 16-bit WAV**。`BackgroundAudioPlayer` 读文件要靠 ffmpeg，但 HK 主机没装 ffmpeg，所以用仓库里已有的 WAV 解码（`src/tts/wav.ts`）自己读，混音器也是 48kHz 单声道。转换脚本放在 `services/` 下，像预录语气词一样离线生成。
9. **网页开关**。在右上角字幕开关旁边放一个 `Toggle`，图标用 `lucide-react` 的 `Volume2` / `VolumeX`，无障碍名称为“背景音”。默认开启，不记住选择。关闭时只在浏览器里取消订阅 `background_audio` 音轨，Agent 照常运行，重新打开就能接上当前档位。这个开关不影响 Agent 的语音。

## 考虑过的方案

- **照搬旧项目（整段 JSON + 关键词正则 + 浏览器 `HTMLAudio`）**：
  - 输出 JSON 就得等整段回复生成完才能解析，没法流式合成。而且 Dolphin 经常不遵守格式，旧项目只好写了三层兜底解析。
  - 关键词规则太宽（`/干/`、`/硬/`、`/嗯+/` 会命中“干什么”“硬件”），和模型给的标签互相冲突，最后播哪一档取决于哪个先到。
  - 浏览器单独播放的声音不在回声消除的参考信号里，会被麦克风收进去，造成误打断（`server.md` 修正表第 8 条当初没做 BGM 分轨，就是因为这个风险）。
  - 切档是直接暂停再从头播放，而且一收到文字就切，不等这段回复真正开始播放。
- **由第二个模型给对话打档**：判断更稳定，但每轮都多一次调用，增加延迟和费用。只有发现主模型标签质量不够时才考虑。
- **5×5 组合（环境 × 强度）**：每种组合都要单独一个文件。将来如果要加环境音，改成分层：环境底音和强度层各有一个标签，同时混音播放（5+N）。清单结构现在就预留“层”这一级，但只实现强度这一层。

## 取舍

- **依赖模型遵守格式**：如果模型漏写标签，背景音就停在当前档位，不会乱跳；但升档可能偏慢。要实测 Dolphin 在 `rouyi` 人设下写标签的比例。
- **回声消除不能完全消掉**：在回声消除参考信号里，不代表能消干净。背景音量要压在人声之下，用户说话时可以考虑压低背景音（ducking），先实测再决定要不要做。
- **素材本身**：循环素材的首尾要能无缝衔接。low 和 mid 只有 10 秒，听起来可能会有重复感，接上之后要试听。
- **语气词**：预录语气词播放期间，背景音保持原来的档位，等真正的回复开始播放才切换。

## 待定

- **具体数值**：标签写法（`<bg:mid>` 或中文 `<背景:中>`）、淡入淡出时长、各档音量，在实测后再定。
